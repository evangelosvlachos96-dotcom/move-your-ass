One trainer, their clients, and a private video library.

A private platform for a personal trainer with tens to low hundreds of clients. Clients register, the trainer approves them by hand, and from then on they log in to stream the workout library. ASP.NET Core 10 API and an Angular SPA, served from a single origin. Not a marketplace, not multi-tenant, and no booking.

Start in four steps

Prerequisites: .NET 10 SDK, Node 22+, and a PostgreSQL database. Configuration lives in user-secrets, never in the repo.

1 · Restore and configure

dotnet restore, then dotnet user-secrets set "ConnectionStrings:Default" "…" --project src/Mya.Api.

2 · Create the database

dotnet ef database update --project src/Mya.Infrastructure --startup-project src/Mya.Api. The seeder creates the two roles and the first admin from configuration.

3 · Run the API

dotnet run --project src/Mya.Api — listens on http://localhost:5077, with Swagger at /swagger.

4 · Run the SPA

cd web && npm ci && npm start — opens at http://localhost:4200. Checks: dotnet test, npm run lint, npm run build.

What it does

Two roles, one trainer. There is no public path to becoming an admin, and no booking or calendar: this is a video library.

Approved registration

A client registers with email and the account stays inactive until the trainer approves it. The trainer can also reject, suspend or reactivate any account.

Password login, one session

Email and password. Short-lived JWT access tokens held in memory, with a rotating refresh token in an HttpOnly cookie. A new login replaces the previous session.

Email invitations

The trainer can create an account directly. The client receives a single-use, expiring link and chooses their own password; no temporary password is ever emailed. Resending invalidates the earlier link.

Video library

Designed, not yet built. The trainer uploads and publishes workouts; clients filter and stream them. Video bytes go straight between the browser and the provider, never through the API.

Transactional email

Every outbound email is written as a row in the same transaction as the change that caused it, then dispatched by a background service. A dead mail provider cannot roll back an approval.

Current status

Accounts are built: registration, approval, invitations, roles, session control and the admin UI. Deployment is in progress. The video library is designed and not yet built. Booking was dropped from the product.

Two design decisions worth knowing

Both are enforced by the database or by a test, not by convention.

  1. Single-use invitations are enforced by the database, not the UI. Consuming a setup link is one conditional UPDATE whose affected-row count decides the winner, so two concurrent submissions of the same link produce exactly one activation. The same rule governs duplicate emails: a unique index decides, never a pre-check query.
  2. The SPA and the API share one origin. The API serves the Angular build from its own wwwroot. That is not tidiness: the refresh token lives in a SameSite=Strict cookie, which a browser will not send across hosts. One origin makes the cookie work and removes CORS from production entirely.

Four layered backend projects — Mya.Api, Mya.Application, Mya.Domain, Mya.Infrastructure — with feature folders inside each. Mya.Application may use EF Core’s abstractions but never the database provider or ASP.NET, and Mya.Domain references nothing at all; an architecture test fails the build otherwise. API, SPA, infra and docs ship in one mono-repo, so an API contract change is one commit and one PR.
