Training Platform

One trainer, their clients, a video library and a calendar.

A private platform for a personal trainer with tens to low hundreds of clients. Clients register, the trainer approves them by hand, and from then on they log in to stream the video library and book 1:1 sessions. ASP.NET Core 10 API, Angular SPA, deployed on Azure. Not a marketplace, not multi-tenant.

Start in four steps

Prerequisites: .NET 10 SDK, Node 22+, Docker for the test database, Azure CLI. Configuration lives in user-secrets, never in the repo.

1 · Restore and configure

dotnet restore, then dotnet user-secrets set "ConnectionStrings:Default" "…" --project src/Mya.Api.

2 · Create the database

dotnet ef database update --project src/Mya.Infrastructure --startup-project src/Mya.Api. The seeder creates the two roles and the first admin from configuration.

3 · Run the API

dotnet run --project src/Mya.Api — listens on https://localhost:7001.

4 · Run the SPA

cd web && npm ci && npm start — opens at http://localhost:4200. Tests: dotnet test and npm run test.

What it does

Two roles, one trainer. There is no public path to becoming an admin.

Approved registration

A client registers with email and the account stays inactive until the trainer approves it. The trainer can also reject, suspend or reactivate any account.

Login with a one-time code

Email and password, confirmed by a code sent to the inbox. JWT access tokens with rotating refresh tokens.

Video library

The trainer uploads and publishes content. Clients stream it as HLS straight from Blob Storage — the bytes never pass through the API.

1:1 booking

A calendar showing only free slots, up to five active bookings per client. The trainer publishes weekly availability and can move or cancel any session.

Change requests

Clients ask to move or cancel a booking and can withdraw the request while it is pending. The trainer gets an email and approves or rejects.

Current status

Phase 1 is built and deployed: registration, approval, email 2FA, roles, session control. Booking, calendar, videos and change requests are designed but not yet built.

Two design decisions worth knowing

Both are enforced by the database or by a test, not by convention.

  1. Booking conflicts are resolved by the database, not the UI. Claiming a slot is a single conditional UPDATE whose affected-row count decides the winner. Polling, tab sync and idempotency keys sit on top as UX; none of them is the guarantee.
  2. Every user-initiated mutation carries an Idempotency-Key header. The key is generated when the user forms the intent — the dialog opens — not when the button is clicked. Deduplicated per user for 24 hours, replaying the original response.

Four layered backend projects — Mya.Api, Mya.Application, Mya.Domain, Mya.Infrastructure — with feature folders inside each. Mya.Application may not reference EF Core or ASP.NET; an architecture test fails the build if it does. API, SPA, infra and docs ship in one mono-repo, so an API contract change is one commit and one PR.
